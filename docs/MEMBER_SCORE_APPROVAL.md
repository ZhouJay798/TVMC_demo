# L2 成员核算得分后再门限解密

本次改动对应新版论文第 4.7 节算法 6 第 7 行：至少 t 位成员批准追踪请求，从日志重算每个 E_cid，再返回带签名和证明的部分解密。

## 实际流程

1. 初始化双 DKG、成员登记；发行前登记参数承诺和加密码本，发行清单签名绑定码本哈希及接收人。
2. 固定取证对象，披露探针，读出可疑码字。原主流程先筛查、再归因。
3. 追踪者构造完整得分批次，绑定 group、code_key.kid、证据哈希、可疑码字和请求前日志头，并先将 score_request 写入日志。
4. 每位 ScoreApprover 只接收自己的份额、身份私钥、固定公钥登记和本地证据读取器。请求不能自行提供读取函数。
5. 成员核验日志头/哈希链、参数承诺、证据先于披露、码本先于发行且发行先于取证、发行清单签名、接收人登记及码本哈希、每位 0/1 证明。
6. 文件路径由成员配置的读取器重算可疑码字。API 路径直接从日志核验端点承诺、探针开封及哈希、签名原始响应、门限人数和码字完全一致，拒绝登记的合法端点。当前 API 读出阈值固定为 1。
7. 各成员独立计算所有副本的得分密文，整批与请求比较。替换成指纹位密文、改动得分或遗漏副本均在使用份额之前拒绝。
8. 通过后预留本成员的单次使用状态，再逐个计算部分结果和证明。部分结果沿用绑定 group、证据、可疑码字、cid、a、b 的上下文；另签署整个请求哈希的批准。
9. 主流程记录 score_approval，验证各部分结果并合并得分。public Judge 对新版本结果额外核验批准人数、签名、请求哈希、顺序及所有结果归属。
10. 比较阈值，核验发行清单定位成员。仍然不解密完整指纹码字。既有 API 转发反驳和去位重评分保留。

## 安全边界

- 这次实现是成员检查入口及逐成员重算，不是独立机器上的部署。主程序仍持有全部份额；操控整个进程的攻击者可以绕过入口。真正隔离需独立服务/设备保管份额。
- trusted_head 和证据读取器必须通过成员可信配置提供；当前演示由本地初始化提供，不是 CA 或外部独立见证的替代。
- ScoreApprover 的单次状态在内存中，主追踪同时依赖日志和探针组停用；生产服务还需持久化原子预留、崩溃恢复和并发控制。不得把该类直接暴露为无状态网络接口。
- 达到门限的恶意成员仍可合谋解密码本；一个合法得分也可能透露部分信息。单次评分不是零泄漏保证。
- 文件读出信任本地配置的真实模型读取器；API 证据校验不等于证明外部服务从不转发，仍需反驳机制。
- 本次没有重写探针托管或反驳重评分授权机制，没有新增 CA，也没有宣称完成全部论文安全证明。
- 历史 trace 不含新协议版本字段，独立验证继续支持原格式；新生成 trace 标记 member-checked-scores-v1 并强制核验批准。历史结果不能当作成员核验已运行的证据。

## 验证

执行 `.venv/bin/python -m pytest -q`。新增测试验证逐位密文冒充、得分篡改、遗漏副本、码字替换、错误密钥/检查点/证据、日志篡改在部分解密前拒绝；验证正常批次、重复请求和 API 签名证据到公开 Judge 的链路。

API 新测试使用明确标记的合成响应，不是新的真实模型 API 鲁棒性实验；既有真实模型结果及未完成的 API 验收仍以原报告为准。
