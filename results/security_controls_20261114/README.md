# CA、公钥替换与 API 识别对照实验（2026-11-14）

## 结论

13 类受保护的协议攻击各运行 5 轮：关闭对应校验时共 65/65 被接受，启用完整对应校验时 0/65 被接受。3 类正常业务各 5 轮，两组均 15/15 正常通过。另做 3 类边界对照各 5 轮：两份份额不足以解密；预置信任根被控制、达到门限的成员合谋依然可突破。

真实本地 HTTPS 诊断测试 U1、U2、U3、未加指纹基座、转发 U1 五种场景，每种由三位采集者采集。归属诊断与转发反驳结果见表。协议的 5 轮并不意味着 API 每场景也重复了 5 轮。

## 实验设计与边界

- 防护关闭只在 experiments/ 下的独立实验脚本中实施，生产模块没有增加跳过 CA/验签的选项。实验未导出任何 CA 或成员私钥。
- 每轮协议实验使用新生成的 CA、成员密钥和双 DKG。不同场景关闭的是其对应控制，不能把所有对照统称为“只关闭 CA”。
- “接受”包括接受伪造申请/清单、接受错误交付包、解出内层数据密钥或泄露指纹位等不同影响，原始 JSON/CSV 的 impact 字段区分；接受坏记录不等于已经泄露完整模型。
- 接收公钥替换测试实际执行 HPKE 封装与攻击者解封，测试内层密钥保护；取得内层包仍受外层门限约束。
- 密文篡改对照只证明仅验清单签名不足以检查包的完整性；并未声称攻击者绕过 AES-GCM 标签恢复了模型明文。
- 防回滚组显式提供最新可信日志头和最低 CRL 序号。仅有 CA 根不能保证撤销信息/登记状态最新；默认启动时不保存这些状态仍有风险。
- API 复用已经可信交付的模型和已经披露的探针，参考码字通过原始副本读回取得；采用明文参考 Tardos 评分做诊断，不冒充对已停用组发起新的 L2 门限调查。正式门限 API/转发链路见 ../acceptance_20261114。

## API 证据对照

| 操作 | 缺少对应校验 | 启用对应校验 |
|---|---|---|
| 错误 TLS 身份/公钥指纹 | 接受=True，命中=见归属表 | 接受=False |
| 篡改采集响应，将 U1 伪装成 U2 | 接受=True，命中=[2] | 接受=False |
| 一名采集者签署与另外两人不同的码字 | 接受=True，命中=[2] | 接受=False |
| 将转发误认成模型权重泄漏 | 接受=True，命中=见归属表 | 接受=False |
| 已登记合法端点的排除 | 直接运行通用证据核验接受 | API 专用核验拒绝作为泄漏证据 |

合法端点排除使用上次真实 API 的完整签名证据重放，在登记表补充该端点后做核验对照：省略端点排除的 judge_file 仍通过，judge_endpoint 拒绝。它是存量证据复核，不是又一次现场取证。

API 日志中可能出现一次 BrokenPipeError：这是错误 TLS pin 实验主动断开连接后，服务端读取失败的预期副作用；以脚本最终断言和 api_results.json 判断实验是否完成，不把该日志当成成功的攻击。

## 仍未解决的问题

1. CA 私钥或验证端信任根被控制，证书机制本身不能挽救。真实 CA 首次身份核验、密钥隔离、撤销状态分发尚需部署。
2. 达到门限的成员可以离线合谋解密码本；审批日志只能约束按协议执行的成员。
3. 指纹证明模型副本来源，不直接证明谁窃取了 API 密钥，也不能仅凭命中认定托管方主动泄漏。API 凭据盗用仍需访问认证、权限与请求审计。
4. 本次没有解决上次发现的模型平均、基座复位、公开基座低秩截断导致的漏判。
5. 本地同进程/同主机实验不等于多机构独立服务、恶意 OS 环境或全面渗透测试。
